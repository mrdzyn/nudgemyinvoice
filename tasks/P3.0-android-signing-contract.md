## Objective

Add a reusable Android signing contract for Flutter, React Native, and native Android/Kotlin projects so debug signing, release/upload signing, secret names, CI injection, artifact verification, recovery, and Google Play App Signing are handled consistently without sharing production key material across apps.

## Context

Android projects currently inherit general release/security guidance but no cross-stack signing standard. The template should standardize the process and variable names while keeping each app's release/upload key and passwords unique.

## Forbidden scope

- committing any real keystore, upload key, signing key, password, or secret;
- defining one shared release/upload key or password across products;
- changing Android application IDs/package names;
- changing app-store credentials;
- changing capability selectors beyond wiring the Android signing document to existing Android/Google Play/Huawei AppGallery selectors;
- weakening human release approval, secret-handling rules, or existing CI controls;
- merging without explicit owner approval.

## Acceptance criteria

- [x] One canonical Android signing contract applies to Flutter, React Native, and native Android/Kotlin.
- [x] Debug signing uses Android tooling defaults and is never valid for production release artifacts.
- [x] Release/upload keys are unique per app by default; actual password values are not standardized across apps.
- [x] Canonical signing variable/secret names are defined.
- [x] Local and CI secret-handling patterns are documented.
- [x] Google Play App Signing vs upload-key responsibilities are clearly separated.
- [x] AAB and APK verification commands are documented.
- [x] The contract requires project release CI to fail closed when signing inputs are missing or artifacts are unsigned/debug-signed.
- [x] Android signing guidance becomes required when the Android platform, Google Play storefront, or Huawei AppGallery storefront is selected.

## Security / privacy considerations

Release/upload private keys and passwords are critical secrets. Base64 encoding is transport encoding, not encryption. Key material must remain outside Git, documentation, logs, prompts, and build artifacts.

## Design / accessibility considerations

Not applicable.

## Third-party integration considerations

Google Play App Signing is documented as the preferred/required path according to current Play policy, but current official Google documentation remains authoritative.

## Release / store / deployment considerations

This is release-critical policy. Production AAB/APK generation must use approved release/upload signing and remain human-gated.

## Capability profile changes

No new selector. `release/android-signing.md` is required when:
- `platforms` includes `android`; or
- `storefronts` includes `google-play` or `huawei-appgallery`.
