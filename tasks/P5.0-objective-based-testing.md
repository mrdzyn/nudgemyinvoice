## Objective

Reduce unnecessary AI-agent test execution and token consumption by making testing objective-based and risk-proportionate.

The default rule is:

```text
task / acceptance criteria
→ define the test objective
→ run the smallest targeted automated checks that can prove it
→ objective satisfied?
   ├─ no: fix / targeted retest
   └─ yes: stop expanding automated tests
→ manual QA
→ PR / required CI
→ independent audit
→ human approval
```

## Context

The current template correctly requires validation but can be interpreted by agents as “run every available test.” That is wasteful for small, localized changes and can consume excessive model context/tokens without improving confidence.

Independent review also identified a second-order risk: the testing policy itself must not create more per-task context cost through duplicated instructions. `docs/TESTING.md` is therefore the canonical policy; always-loaded/runtime artifacts should contain only the minimum pointer and task-specific evidence fields.

Testing must answer a concrete question. Once the objective is demonstrated, the coding agent should stop broadening its own test loop unless risk, blast radius, failures, or an explicit release gate justify broader coverage.

Required PR/CI checks remain authoritative and are not bypassed by this optimization.

## Forbidden scope

- disabling or weakening required CI checks;
- deleting valid regression tests merely to reduce runtime;
- skipping mandatory security/privacy/tenant/auth/payment/migration/release checks;
- claiming manual QA or automated validation occurred when it did not;
- treating a passing targeted test as proof of unrelated behavior;
- replacing repository-required release/regression gates with agent discretion;
- merging without explicit owner approval.

## Security / privacy considerations

Risk-proportionate does not mean risk-tolerant. Changes involving authentication, authorization, tenant isolation, credentials, cryptography, payments, migrations, shared security controls, production infrastructure, or release signing must use broader validation appropriate to their blast radius.

## Design / accessibility considerations

For UI changes, targeted automated validation is followed by the defined manual QA/device/platform check. Manual QA is not replaced by unit/component tests.

## Release / store / deployment considerations

Release candidates and store/deployment gates may require broader regression regardless of how small the final code delta appears.
