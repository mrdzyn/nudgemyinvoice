# P8.0 — Reusable CI/CD Pipeline Foundation

- **Status:** Ready — M3 pending
- **Owner/orchestrator:** Project owner + ChatGPT
- **Implementation agent:** Unassigned
- **Target branch:** `main`
- **Working branch:** None

## Objective

Define an implementation-ready contract for a small, secure, opt-in CI/CD foundation that generated and adopted projects can use without duplicating large amounts of GitHub Actions configuration, while preserving project-specific control over stack validation and release/deployment behavior.

P8.0 is **not** a universal deployment platform. It establishes one reusable common-validation foundation, one stack-extension contract, generated/brownfield adoption rules, and the security boundary between ordinary pull-request CI and privileged release/deployment workflows.

## Context / current baseline

The current template already has two intentionally separate workflows.

### `.github/workflows/ci.yml`

Provides the child-project-compatible baseline:

- Project Baseline validation through `scripts/validate_project_profile.py`;
- project-profile/capability validation;
- a lightweight rejection of tracked local `.env` files;
- `permissions: contents: read`;
- an explicit reminder that projects must add real stack-specific lint, typecheck/analyze, test, build, security, and artifact validation.

This file is intended to remain in generated projects.

### `.github/workflows/template-integrity.yml`

Provides master-template-only validation:

- canonical template inventory;
- master-template project-profile state;
- capability-profile self-tests through `scripts/test_validate_project_profile.py`;
- a repository guard limiting the job to `mrdzyn/ai-native-project-template`.

Generated projects must continue to remove this workflow during greenfield pruning.

### Existing policy that P8.0 must preserve

- `docs/TESTING.md` defines objective-based, risk-proportionate agent validation and keeps required CI separate from the agent's local test budget.
- `docs/RELEASE.md` requires source traceability, known-artifact promotion where practical, explicit human production approval, and rollback/recovery planning.
- `docs/REPOSITORY-SETUP.md` defines branch/ruleset enforcement, required checks, environment protection, secrets/variables, greenfield pruning, and brownfield reconciliation.
- `config/project-profile.json` currently selects product capabilities/platforms/storefronts/integrations; it does not model programming languages or build systems.

## Problem being solved

The template currently tells every child project to add stack-specific CI, but it does not define a reusable composition model.

Without a bounded foundation, generated/adopted projects can drift toward one of two bad extremes:

1. duplicating the same baseline GitHub Actions YAML across many repositories; or
2. building an elaborate shared workflow framework that hides project-specific validation, creates coupling, and expands deployment privilege.

P8.0 must provide a middle path:

- reusable universal validation;
- explicit project-owned stack jobs;
- stable required-check semantics;
- no provider lock-in;
- no ordinary-PR access to release privileges;
- no automatic production release merely because `main` changed.

## Proposed architecture

### Decision: narrowly combined model

P8.0 implementation should use a **narrowly combined approach**:

1. deterministic repository/profile checks remain in scripts so they can run locally and in any CI system;
2. GitHub Actions provides a small reusable orchestration layer using `workflow_call`;
3. the project-owned `.github/workflows/ci.yml` remains the visible entrypoint for PR/push validation;
4. project-specific stack jobs remain explicit in the project repository rather than being hidden behind a universal command runner.

The intended future implementation shape is:

```text
.github/workflows/ci.yml
    ├─ common baseline job → same-repository reusable workflow
    │                       └─ deterministic scripts
    └─ project-owned stack jobs
        ├─ lint / static analysis
        ├─ typecheck / analyze
        ├─ unit / targeted integration tests
        ├─ build / package
        └─ security / dependency checks
```

The exact reusable-workflow filename is an implementation detail, but it must live directly under `.github/workflows/` because GitHub reusable workflows are workflow files and are invoked at job level with `workflow_call`.

### Why not scripts only

Scripts remain the correct home for deterministic repository rules, but scripts alone do not standardize GitHub job permissions, triggers, status-check boundaries, or reusable orchestration.

### Why not a large reusable-workflow framework

P8.0 must not centralize arbitrary stack commands or deployment providers into a complex workflow engine. Child repositories must remain understandable by opening their own `ci.yml`.

### Future central workflow repository

A future central engineering-platform repository may host versioned cross-repository reusable workflows. That is explicitly outside P8.0. P8.0 should first prove the contract using same-repository reusable workflows inherited by generated projects.

## Project-profile interaction

### Decision: no framework/toolchain selectors in P8.0

P8.0 must **not** add Node, Flutter, Swift, Kotlin, PHP, Windows, backend, or other build-stack enums to `config/project-profile.json`.

The existing project profile remains authoritative for product capabilities and release-relevant platform/store selections. It may continue to drive conditional repository requirements already tied to those product choices, such as Android signing guidance.

Stack-specific CI remains project-owned.

### Extension point

Generated/adopted projects declare stack validation by adding explicit jobs to their project workflow using the stack's normal commands.

Examples:

- web / Node: lint, typecheck, unit/integration tests, build, dependency audit;
- Flutter: analyze, test, platform build where applicable;
- native Apple: build/test on an appropriate macOS runner;
- Android: compile/test/build plus release-signing validation only in release context;
- Windows: build/test on an appropriate Windows runner;
- WordPress/PHP: lint/static analysis, PHPUnit/integration checks, packaging;
- backend/server: stack-specific validation and service-boundary tests;
- documentation-only: no artificial language/build jobs.

A future additive machine-readable CI profile may be proposed only if real implementation experience shows that conventions are insufficient. It is not part of P8.0.

## Universal CI contract

Every generated/adopted project should have one common baseline validation path.

### Universal required PR baseline

P8.0 implementation should preserve and reuse:

1. project-profile/core operating-model validation;
2. generated-project cleanup enforcement already implemented by the validator;
3. the lightweight tracked-local-environment-file guard;
4. least-privilege read-only repository access;
5. deterministic failure behavior.

The common baseline may gain narrowly scoped repository-contract checks only when they are genuinely universal and executable without stack assumptions.

### Explicitly not universal in P8.0

The following must **not** be treated as universal baseline checks:

- dependency lockfile presence;
- package-manager audits;
- compile/typecheck;
- application tests;
- application builds;
- release artifacts;
- signing;
- marketplace/store validation;
- deployment metadata.

Those belong to stack-specific or release-specific jobs because documentation-only repositories and many other valid project shapes do not share them.

### Secret-file guard language

The existing tracked-`.env` filename check remains a **lightweight guard only**. P8.0 must not describe it as a comprehensive secret scanner.

A real secret-scanning product or policy may be added by a project or future phase, but is not silently implied by this baseline.

## Stack-specific extension contract

Each project owns its stack jobs and commands.

### Logical job categories

Projects should use the applicable categories:

- `lint` / static analysis;
- `typecheck` or platform analyze;
- `test` for unit/behavior checks;
- `integration` where a real boundary requires it;
- `build` / package;
- `security` / dependency checks;
- release-only artifact/signing validation.

A project does not create empty jobs merely to satisfy a universal matrix.

### Command ownership

Commands should live in the project's native package/build system or small project-owned scripts when that improves local/CI parity.

P8.0 must not introduce a generic configuration file that accepts arbitrary shell command strings merely to centralize them.

### Stable check names

Repositories should make required status checks mandatory only after job names and behavior are stable enough not to deadlock merges.

Renaming a required check is a repository-enforcement change and must be coordinated with the ruleset/branch-protection configuration.

### Hosted CI availability, quota exhaustion, and duplicate-run control

P8.0 must support the canonical CI-unavailable break-glass and trigger-economy rules defined in `docs/REPOSITORY-SETUP.md`. The task-specific requirement is that hosted-CI unavailability cannot permanently deadlock a reviewed PR, while a genuine failing executable check remains outside the exception.

## Required vs optional checks

P8.0 defines four classes.

### 1. Required PR gates

Examples:

- Project Baseline;
- stable stack-specific lint/static analysis;
- typecheck/compile where applicable;
- tests required by the project's risk model;
- build/package where needed to prove merge safety;
- security/dependency checks appropriate to the product.

These are repository policy and still run even when an agent's local validation was intentionally narrow.

### 2. Optional informational checks

Examples:

- expensive extended matrices;
- advisory compatibility checks;
- non-blocking analysis;
- experimental toolchains.

They must not masquerade as required evidence.

### 3. Release-only checks

Examples:

- signing;
- exact release-artifact verification;
- provenance/checksum generation;
- store/package validation;
- migration/recovery readiness.

These do not belong in ordinary untrusted PR execution unless a project has a safe reason and no release secret is exposed.

### 4. Manual QA / human gates

Manual QA remains separate from CI. Store review, device/browser inspection, realistic environment checks, and production approval are not converted into fake automated checks merely for dashboard completeness.

## PR vs release/deployment separation

Ordinary PR CI and privileged release/deployment are different trust zones.

### Pull-request CI

- may validate untrusted proposed code;
- must not have production credentials;
- must not deploy to production;
- should default to read-only repository permissions;
- should not use `pull_request_target` to execute untrusted PR code;
- should remain safe for fork/Dependabot-style restricted execution.

### Main-branch CI

A push to `main` may validate the merged commit and prepare a candidate, but **must not by itself imply production authorization**.

### Release/deployment

Production publishing/deployment requires a separate workflow or explicitly separated job path with:

- human authorization;
- environment/repository protection appropriate to the project;
- release-specific secrets or federated identity only when required;
- exact source/candidate identity;
- release-only validation;
- post-release verification and recovery plan.

Manual marketplace submission remains valid. P8.0 does not require automation of App Store Connect, Google Play, Microsoft Store, WordPress.org, or any cloud provider.

## Security / secrets model

### Default permissions

Common PR validation defaults to:

```yaml
permissions:
  contents: read
```

Implementation may reduce permissions further where feasible.

No common PR validation job should request write scopes by default.

### Reusable-workflow permission boundary

The caller must explicitly constrain permissions. A reusable workflow may maintain or reduce the caller's `GITHUB_TOKEN` permissions but must not rely on being able to elevate them.

### Secrets

The common reusable PR-validation workflow should require **no production or deployment secret**.

Secrets are passed to reusable workflows only when explicitly required and explicitly supplied by the caller or permitted inheritance. P8.0 common validation should avoid that need.

### Fork / untrusted PR behavior

For normal fork PR execution:

- non-`GITHUB_TOKEN` secrets are not assumed available;
- the token should be treated as read-only for untrusted PR validation;
- workflows must not weaken this boundary to make checks convenient.

Dependabot-style PRs should be treated as similarly restricted.

### OIDC / `id-token: write`

`id-token: write` is **not** part of the common PR baseline.

It may be granted only to a future release/deployment job that actually needs GitHub OIDC to exchange an identity token for short-lived external credentials.

Grant it at the narrowest practical workflow/job scope and combine it with provider-side trust conditions and environment/release protection.

The presence of `id-token: write` authorizes requesting an OIDC token; it is not a generic repository write permission, but it is still a privileged trust capability and must not be granted casually.

### Environment-scoped production credentials

Where GitHub Environments are used, production credentials should be environment-scoped when practical. A protected environment may delay secret access until its protection rules are satisfied.

Where the repository's GitHub plan or visibility does not support the desired protection rule, document the compensating explicit human/process gate rather than claiming enforcement exists.

## Generated-project behavior

### Keep

Generated projects keep:

- `.github/workflows/ci.yml`;
- `scripts/validate_project_profile.py`;
- the future P8.0 common reusable validation workflow if implementation adds it;
- project-specific CI additions.

### Customize

Generated projects customize:

- stack-specific jobs and commands;
- required status checks;
- runner selection;
- caches;
- service containers/test infrastructure;
- release-only workflows;
- environment names and protection;
- project/provider-specific secrets and variables.

### Remove

Generated projects continue to remove:

- `.github/workflows/template-integrity.yml`;
- master-only task/history artifacts;
- master-only self-test logic where Phase 6 already requires removal and the child does not deliberately maintain validator internals.

### Master-only

`.github/workflows/template-integrity.yml` remains master-template-only.

P8.0 must not make Template Integrity a required child-project workflow, reusable child dependency, or release gate.

## Brownfield adoption behavior

Use the Phase 6 KEEP / MERGE / ADD / RETIRE process.

For CI/CD:

- **KEEP** a stronger existing pipeline that already satisfies the concern;
- **MERGE** only missing baseline/security/human-gate controls into the existing canonical CI system;
- **ADD** the P8.0 common baseline only when no equivalent exists;
- **RETIRE** duplicate checks/workflows only after confirming their unique behavior has been preserved or deliberately removed.

Do not require a mature project to adopt the template filenames when it already has an authoritative equivalent.

Do not weaken existing protections, runner isolation, secret handling, release approvals, or provider-specific safety controls merely to match the template.

## Testing strategy for the future implementation

### Test objective

> Prove that the reusable CI foundation correctly validates a generated/adopted project, preserves the required baseline, leaves stack-specific checks under project control, and cannot accidentally expose release privileges to ordinary PR execution.

### Minimum automated evidence

Implementation should use the smallest evidence that proves that objective:

1. existing project-profile self-test matrix still passes;
2. master profile validation still passes;
3. the common reusable validation workflow is actually invoked by a PR caller and succeeds on the master template;
4. a generated-project fixture/case retains the child-compatible common CI path but rejects/removes Template Integrity;
5. positive profile cases remain valid;
6. malformed profile/generated-cleanup cases remain fail-closed;
7. if new validator behavior is added, add targeted regression cases only for that behavior.

### Workflow syntax evidence

Prefer proving reusable-workflow syntax by having GitHub Actions parse and execute the caller/called relationship in required CI.

Do not add a new validation dependency solely to lint YAML unless implementation demonstrates that GitHub execution plus existing targeted validation is insufficient.

### Least-privilege evidence

Independent review must inspect:

- top-level and job-level `permissions`;
- absence of production/release secrets from ordinary PR validation;
- absence of unnecessary `id-token: write`;
- fork/untrusted PR behavior;
- release/deployment separation.

### Required CI

Normal path after E2b: one automatic `Project baseline / Common validation` required context (including guarded master-only steps in the canonical master). `Template Integrity` is manual-only and not required on pull requests. Child projects keep the caller and reusable baseline while removing master-only workflows/scripts.

If required GitHub-hosted CI cannot execute because of documented external availability/quota conditions, use the repository's approved CI-unavailable break-glass process in `docs/REPOSITORY-SETUP.md`. That process must require equivalent validation, independent review, an explicit owner/admin decision, and a pull-request-only bypass where supported. It must never convert an actual failing check into an acceptable result.

### Manual QA

For P8.0 implementation, manual QA is repository/process inspection rather than UI testing:

- inspect the PR workflow graph/status checks;
- confirm the common baseline actually runs through the reusable mechanism;
- confirm stack-specific extension points remain understandable;
- confirm no release/deployment action occurs;
- confirm generated-project guidance still removes Template Integrity.

## Edge cases

The implementation and independent review must consider:

1. **Documentation-only repositories:** baseline CI must work without fake language/build jobs.
2. **Monorepos:** common baseline should run once; stack/workspace validation remains project-owned.
3. **Fork PRs:** no production secrets or privileged write tokens may be required.
4. **Dependabot PRs:** treat them as restricted/untrusted for secret assumptions.
5. **Private repositories / plan limits:** environment reviewers and other protections may vary; document compensating controls.
6. **macOS/Windows toolchains:** stack jobs may require non-Ubuntu runners, but universal baseline should not.
7. **Self-hosted runners:** projects must assess isolation and secret exposure; P8.0 does not make self-hosted runners the default.
8. **No lockfile:** must not fail universal CI merely because a repository legitimately has no package manager.
9. **Store projects:** signing/store checks remain release-only and follow existing store/signing guidance.
10. **Provider without artifact promotion:** document an equivalent immutable deployment reference or the limitation; do not falsely claim artifact promotion.
11. **Required-check rename:** coordinate workflow job-name changes with branch/ruleset settings to avoid deadlocking merges.
12. **Reusable-workflow recursion/nesting:** P8.0 should remain shallow; no workflow framework or deep nesting.
13. **Hosted Actions quota exhausted/unavailable:** required-check enforcement must have a documented owner-controlled PR-only break-glass path backed by equivalent validation; genuine test/build/security failures remain non-bypassable by policy.
14. **Duplicate trigger cost:** feature-branch push + pull-request validation must not duplicate the same expensive matrix by default.
