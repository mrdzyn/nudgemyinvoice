## Objective

An authenticated operator opens a saved PostgreSQL invoice, explicitly confirms creation of a PayPal Sandbox DRAFT, sees the real backend state, and safely handles every uncertain or failed outcome. The app never sends, emails, collects or marks anything paid.

## Contract used (existing backend, unchanged)

`POST /api/invoice-drafts/:id/paypal-draft` (session + CSRF + Origin; empty body): `201`/`200` `{paypalInvoiceId, status:"DRAFT", replayed}`; `409 in_progress` / `409 reconciliation_pending`; `422 mapping_refused {reason}`; `502 paypal_mismatch|paypal_rejected|paypal_outcome_unknown {code}`; `503 paypal_disabled|unavailable`; `404 not_found`; `400 invalid_request`; `401`/`403`. `GET /api/invoice-drafts/:id` is the authority for the durable `paypal {state, paypalInvoiceId, lastErrorCode}`.

## Implementation (apps/web only; `apps/api`, `packages/*`, migrations, configuration untouched)

- **Transport** (`invoices/api.ts`): `createPayPalDraft(id, csrf, signal)`. Same-origin relative URL of the validated UUID, POST, `credentials:same-origin`, `no-store`, `redirect:error`, CSRF from memory, NO body, abort. Every documented answer has its own result kind. A success is accepted only as exactly `{paypalInvoiceId (<=64 safe chars), status:"DRAFT", replayed}` with `201`<->`replayed:false` and `200`<->`replayed:true`; anything else on a success status is `uncertain/malformed`, never a created draft. Known error bodies are matched by status AND `error`; unknown refusal reasons or error/status combinations fail closed (`bad-request` for 4xx, `uncertain` for 5xx and network). Diagnostic codes are kept only if `^[a-z0-9_.:-]{1,64}$`.
- **Single flight** (`invoices/paypalRunner.ts`): one request per confirmation; a second start sends nothing; abort/unmount/sign-out drop any late answer; a 60 s timeout aborts and reports UNCERTAIN (an aborted browser request does not prove the server stopped).
- **Pure panel state** (`invoices/paypalPanel.ts`): a POST can only follow `open-confirm -> confirm`; cancel, Escape, mount, render, reload and navigation never POST. After an uncertain/in-flight answer the panel is `unverified`: create is NOT offered until the durable state has been re-read. A `disabled` answer is not probed again. `canOfferCreate` allows a new explicit attempt only from durable `none`, `rejected` or `unknown`; never from `created`, `mismatch`, `pending`, `creating`.
- **Panel** (`features/saved/PayPalDraftPanel.tsx`): states not-created, disabled, creating (accessible `role=status`), created (validated id, DRAFT, replay flag, "customer not emailed"), mapping refused (safe reason, "never rounds silently", local invoice unchanged), in progress, reconciliation pending, outcome unknown ("A PayPal draft may or may not exist", neither failure nor success), rejected (explicit retry), mismatch (alert, manual investigation, NO retry), transport failure, 401/403/404/invalid fail closed. The confirmation dialog (existing accessible `Dialog`: focus on Cancel, trapped Tab, Escape cancels, focus restored) names the exact invoice id, customer, currency, server-computed total and due date and states: a Sandbox DRAFT is prepared, the customer is NOT emailed, no payment is collected, no invoice is sent, it happens only because the operator confirms.
- **Durable refresh**: after every POST answer the page re-reads GET detail (read-only, coalesced, aborted with the screen, only lands on the invoice it asked for) and the GET is the authority. "Check status" is read-only (never POST). There is no polling loop and no automatic retry.
- **Copy**: the saved-page notices and the shell notice no longer claim "nothing was sent to PayPal / not created in PayPal"; they distinguish the local PostgreSQL save from the explicit PayPal Sandbox draft, and always say the customer is not notified and nothing is collected. The synthetic preview keeps its own simulated panel and never receives the capability.
- **Found by the browser journey and fixed:** the detail validator rejected the real `lastErrorCode` values that contain a colon (`http_422:invalid_parameter_value`), so a rejected operation could not be read back (the panel kept showing "Not created" next to a rejection notice). The pattern now matches the database constraint; unit tests cover the codes.

## Audit remediation: MAJOR-1 (fix SHA `9b367fb73ea420a179ae853bea9c430405d205fe`)

Independent audit of `d8b715ffbbc7d4308beb6653432dc3543240df6c` returned FIX REQUIRED (MAJOR-1). Frontend, tests, evidence and docs only; the backend, provider adapter, state machine, owner scope and configuration are untouched. Evidence above stays attributed to `17c13e0`/`d8b715f`; the results below are new.

**Defect (confirmed from source):** after a `paypal-mismatch` or `created` POST answer the reducer left `unverified=false`, while the `invoice` prop still described the pre-POST state (`none`). `canOfferCreate("none", ui)` was therefore true before the authoritative GET landed, and a failed GET (`readFailed`) did not block it, so a second create/retry stayed available. The earlier 89/89 journey only exercised a successful, immediate GET.

**Fix (`invoices/paypalPanel.ts`, `PayPalDraftPanel.tsx`, `SavedDetailScreen.tsx`):**
- **Every POST answer fails closed.** `result` always sets `unverified`. Creation is blocked while `unverified && verifiedWith !== invoice`: it is unlocked only by a read-back that produced the exact invoice object currently shown (a different object, a stale one or a failed one never unlocks it).
- **Read-backs are bound to their confirmation.** A `seq` counter increments on each confirm; the read started after an answer carries that `seq`, and a late read for an earlier confirmation (or one arriving while a newer POST is in flight) is ignored, so it cannot clear or flag a newer guard.
- **Failed/malformed/aborted GET never unlocks**, for POST read-backs and for Check status alike; `readFailed` shows a stale-data warning.
- **`created` is cross-checked:** a read-back only verifies a `created` answer if the durable state is `created` with the SAME PayPal id; a contradicting read (still `none`, another id, `unknown`) is a failed verification.
- **No blind retry from stale state:** `mapping-refused`, `disabled`, `not-found`, `forbidden` and `bad-request` set `locked`, which no read-back lifts (the panel says creating "is not offered again from this view"); `mismatch` and `created` never offer create even when verified.
- **Eligibility is judged against what the operator sees:** `canOfferCreate(invoice, ui)` takes the shown invoice, and `open-confirm` re-checks it in the reducer, so the button, the dialog and the reducer cannot disagree.
- **The post-POST read is always a fresh GET** (`refresh({fresh:true})` drops a read that started before the answer instead of joining it).
- Unverified view: while awaiting, the panel shows "Saved state not yet confirmed" with Check status only (for `created` it says the saved record has not been re-read yet); it never claims "not created" or offers Create.
- Preserved: explicit confirmation, single flight, CSRF, 401 invalidation, 60 s timeout = uncertain, owner scope, no automatic POST.

**Tests.** An existing reducer test asserted the defective behaviour ("created/mismatch/rejected/... do not by themselves block the next explicit action" expected `unverified=false`); it was replaced by its opposite (every answer fails closed) rather than kept. No other test was weakened; the old canOfferCreate/readback tests were adapted to the new signatures and tightened. New: 22 reducer/view regression tests, including mismatch + delayed GET, mismatch + failed GET, created + delayed GET, created + failed GET, created + malformed/contradicting GET, mapping refused + stale `none`, uncertain + failed GET (and a failing Check status), valid read-back offering only legitimate actions, a read-back valid only for the exact invoice object, a stale read-back unable to clear a newer guard, and a read-back arriving mid-POST. Web suite 554 tests (was 526).
