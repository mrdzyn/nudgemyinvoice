## Objective

Connect the real authenticated Review screen to the EXISTING `POST /api/invoice-drafts` and a real read-only saved-invoice page to the EXISTING `GET /api/invoice-drafts/:id`. No new backend route, migration, dependency or configuration. "Saved in PostgreSQL" is never presented as "created in PayPal Sandbox", and no save implies the customer was notified.

## Existing backend contract (unchanged)

- POST: `app.requireOperator`, Origin check, `X-CSRF-Token`, optional `Idempotency-Key` `^[A-Za-z0-9_-]{8,128}$`, strict `invoiceDraftSchema` body. Responses: `201 {id, draft, totals, paypalInvoiceId, replayed:false, createdAt}`, `200 ... replayed:true` (same key + identical body), `409 idempotency_conflict`, `400 invalid_request|invalid_idempotency_key`, `422 invalid_draft`, `401`, `403`.
- GET `/:id`: the same fields plus `paypal {state, paypalInvoiceId, lastErrorCode}`; `404` for unknown/non-UUID ids.

## Acceptance criteria and where they are met

1. **Transport** (`invoices/api.ts`): relative same-origin URL, `credentials:"same-origin"`, `cache:"no-store"`, `redirect:"error"`, `Cache-Control: no-store`, `Content-Type`, `X-CSRF-Token` from volatile memory, `Idempotency-Key`, `AbortSignal`. The body is rebuilt by `saveBody()` from exactly the seven draft keys (no totals, ids, status or fixture fields).
2. **Keys** (`invoices/idempotency.ts`, `keyLedger.ts`): 128-bit CSPRNG base64url, volatile memory only, never displayed or logged. A key is bound to the exact serialized body: same body -> same key; changed body -> never the old key.
3. **Lifecycle** (`saveRunner.ts`, `useRealSave.ts`, `ReviewScreen`): client validation first; offline blocks locally with no request; single flight (double click = one POST); 201 created, 200 replayed, 409 conflict (Save blocked until an explicit "Use a new key and keep my edits"), 400/422/403 recoverable with edits kept, 401 -> `expire(epoch)` through the C1 controller, abort on unmount/logout/session end, stale and late results dropped.
4. **Uncertain outcomes**: network loss, a 5xx, a malformed success body and a 20 s timeout are `uncertain`, never failure. The form is locked, and the only paths are "Retry the same save" (same key, identical body, replays) or an explicit "Edit details and save as a new draft" that warns a second draft may be created.
5. **Validation** (`domain/serverInvoice.ts`): exact keys, UUID id, ISO instant, bounded text, supported currency, decimal strings, real dates, and totals equal to an exact BigInt recomputation (shared with C2). 201 must say `replayed:false`, 200 `replayed:true`; the detail must be the record requested; the PayPal object is exact (`state` enumerated, id/code bounded). Anything else fails closed.
6. **Detail** (`features/saved/SavedDetailScreen.tsx`): loads by id after a confirmed save; loading, success, 401 (session ends), 404, offline, 5xx, malformed, 403; cancellation and stale-response protection; shows the real UUID, customer, currency, due date, persisted creation date, server totals and the read-only PayPal state. There is no fixture, estimate or placeholder path.
7. **Isolation**: real mode blocks `open-detail`, `save-invoice`, `paypal-created`, `paypal-override` and navigation to `detail`/`saved`/`review`; the dashboard keeps its synthetic samples visibly labelled and unopenable; PayPal creation is not offered (deferred to C5); the preview (`App.tsx`) never receives `save`/`getInvoice` and is unchanged. No list endpoint (C4), no editing (D4).
8. **Privacy/security**: nothing persisted in browser storage or URLs (the URL carries no id; the id lives in React memory); no PII in logs; CSP `connect-src 'self'`, Origin/CSRF/session/immediate-logout unchanged; no test fake in the production bundle (the journey's launcher lives under `design/evidence`).
