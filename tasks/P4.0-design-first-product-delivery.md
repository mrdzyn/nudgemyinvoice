# P4.0 — Design-First Product Delivery Workflow

- **Status:** Review
- **Owner/orchestrator:** Project owner + ChatGPT
- **Implementation agent:** ChatGPT
- **Target branch:** `main`
- **Working branch:** `feat/design-first-product-delivery`

## Objective

Make design-first delivery the default operating model for every project/phase that includes user-facing UI.

The default UI flow becomes:

```text
requirements in Markdown
→ screen map + user flows
→ screen designs/mockups
→ human design approval
→ UI shell implementation
→ wire business logic/data/APIs
→ automated + behavioral tests
→ integration/device validation
→ pull request
→ independent audit
→ human merge approval
→ release
```

## Context

The existing template establishes design-system guidance but still allows agents to move too directly from task definition into implementation. The desired workflow separates product requirements, visual/interaction decisions, shell construction, and runtime wiring so UX problems are discovered before business logic and infrastructure become coupled to the UI.

Testing requirements are defined from the task/requirements up front. Executable tests are added alongside wiring and integrated behavior rather than postponed as an afterthought.

## Forbidden scope

- changing product-specific brands or starter token values;
- changing security, privacy, store, signing, or deployment policy except where the workflow references existing gates;
- requiring screen design for backend-only, API-only, infrastructure-only, migration-only, or documentation-only tasks with no user-facing UI impact;
- treating mockups/Figma as authority to redefine approved product behavior;
- requiring production API/data wiring merely to preview or approve a UI shell;
- weakening independent review, human merge approval, or production release gates;
- merging without explicit owner approval.

## Acceptance criteria

- [x] AGENTS defines the design-first workflow and when it applies.
- [x] UI work cannot move from requirements directly into substantial wired implementation without the design gate.
- [x] Screen map/flows and required states precede screen design.
- [x] Human approval of screen/design direction precedes substantial UI shell implementation.
- [x] UI shells are allowed to use fixtures/stubs/sample data and remain decoupled from production wiring.
- [x] Business logic, persistence, APIs, state, integrations, and security-sensitive wiring follow the approved shell.
- [x] Testing expectations are identified from requirements and executable tests are added with wiring/integration.
- [x] Task contracts explicitly record UI/non-UI delivery mode, design artifacts, approval state, shell scope, and wiring/test scope when UI is involved.
- [x] Design guidance defines screen-design and shell definitions of ready/done.
- [x] README initialization instructions teach the design-first sequence for greenfield and brownfield UI projects.
- [x] Backend/infrastructure tasks may bypass the visual-design gate when no UI is affected.
- [x] Independent audit and human approval remain final pre-merge gates.
- Exact-head Project Baseline and Template Integrity must be green in GitHub before merge; GitHub checks are the source of truth.

## Security / privacy considerations

Screen designs and shells must not contain real production secrets, customer data, or sensitive production datasets. Fixtures/sample data should be synthetic or sanitized. Design approval cannot authorize weakening authentication, authorization, privacy, or other security boundaries.

## Design / accessibility considerations

This task strengthens design/accessibility sequencing. Required states, accessibility behavior, responsive/adaptive behavior, and platform conventions must be considered before shell approval.

## Release / store / deployment considerations

No release behavior changes. Existing human production-release gates remain intact.
