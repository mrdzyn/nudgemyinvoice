### Runtime and data boundary

```text
Authenticated React dashboard
  └─ AG Studio data source / server-side paging adapter
       └─ same-origin Fastify analytics routes
            ├─ verified session → TrustedActor.operatorId
            ├─ strict request/response Zod schemas
            └─ PostgreSQL owner-scoped query/aggregate
```

AG Studio receives only bounded DTOs returned by Fastify. It never connects to PostgreSQL, PayPal, or Render directly. Operator identity comes exclusively from the validated session and SQL predicates; request bodies cannot select another operator. Keep the existing keyset-paginated `POST /api/invoice-drafts/search` exclusively for grid rows. **A separate authenticated, strict, bounded `POST /api/analytics/summary` aggregate contract is mandatory for every KPI, chart total, and time series**; no chart or KPI may derive a population total from the current page, a client-loaded subset, or `MAX_LOADED_ROWS`. It aggregates all rows matching the authenticated operator and the request's supported filters in SQL, independent of grid pagination. All protected reads are `no-store`; all search terms remain in POST bodies, never URLs or browser storage. Analytics responses omit customer names/e-mails and invoice IDs unless a separately approved drill-down requires an existing owner-scoped read.

**Required aggregate contract** (`POST /api/analytics/summary`, versioned and strict):

- Request accepts only a strict filter object: optional `fromInclusive` and `toExclusive` UTC instants, an explicit IANA `timeZone` used for calendar buckets, supported currency and durable PayPal draft-state groups, and optional bounded `q` search text. The range applies to invoice `created_at`, with inclusive start/exclusive end; `fromInclusive < toExclusive`, a maximum 366-day interval, and a valid timezone are required. The UI converts the selected local calendar interval to UTC instants using a tested timezone-aware routine; DST days may be 23 or 25 hours. The returned buckets group the entire filtered population by local calendar date in the requested timezone. Invalid/missing timezone or malformed/reversed/oversized ranges fail closed. All filters use the same semantics as the owner-scoped grid search; `q` travels only in the POST body.
- Currency summary returns one row per ISO currency with full-population invoice count, counts by durable draft-state group, and exact sum in that currency's integer minor units, plus currency code and exponent. Time buckets carry currency code/exponent and exact minor-unit sums/counts. Never return a cross-currency grand total, compare amounts across currencies, or imply PayPal Sandbox `DRAFT` means sent, paid, unpaid, overdue or settled.
- The aggregate query uses the validated session `TrustedActor.operatorId` in SQL and computes over **all matching owned rows before grouping**, not the cursor page, loaded rows or a bounded subset. Keep result cardinality bounded by the date-range limit and allow-lists; do not cap source rows. Apply parameterized search, date and enum predicates. No PayPal tokens, request digests, raw provider payloads, audit rows, customer data, invoice IDs or model-supplied fields are returned.
- The existing cursor endpoint remains the source only for bounded invoice grid rows. AG Studio KPI values must equal the independent SQL full-population aggregate for the same filters; grid pagination cannot change the aggregate.

**Invoice grid DTO** is separate: opaque local invoice UUID, created/due date, currency, exact total decimal string plus currency code, line count if needed, and durable PayPal draft state (`none | progress | created | attention`). It remains owner-scoped and paginated; do not expose PayPal tokens, request digests, raw provider payloads or audit rows.

The web app may trigger it only from an authenticated, CSRF-protected explicit operator action with the hard limits below. Pass only an immutable, server-computed aggregate snapshot (never customer names/emails, invoice text, PayPal IDs/tokens, session/CSRF values, raw invoice rows or free-text search). Render retains task arguments and returns for 30 days, so the snapshot and short output must be minimized and retention accounted for. The task writes nothing to the application DB. The result is advisory, validated as bounded plain text, shown as generated insight, and is not saved unless a separate explicit report-save action is later approved. No background scheduling: Render Workflows currently has no native scheduler.
- Workflow provider access, if separately approved, uses server-side OpenAI credentials and the existing single-provider architecture. ### Workflow retry, timeout, concurrency and cost bounds

Render currently retries a task up to three times by default (four total attempts), and its default task timeout is two hours. The prototype task must explicitly set **`retry: { maxRetries: 0 }`** and **`timeoutSeconds: 60`**; OpenAI SDK retries must also be set to zero, and the provider request timeout must be at most 30 seconds. A timeout/uncertain provider result returns a bounded unavailable state and is never automatically resubmitted. Retries are zero because a retry can duplicate provider charges even though the task has no database write.

Enforce **one active insight run globally**, with an atomic durable lease/unique active-run guard acquired by Fastify before calling Render and released on terminal completion or after a bounded stale-lease expiry. Because this project supports exactly one operator, this also limits concurrency per operator. A busy run returns `429`; no queue or background/repeated trigger is offered. Allow at most **5 explicit runs per UTC day and 50 runs total through Dec 15**. Fail closed on missing/uncertain counters, Render 429, timeout or unverified completion. Input is a versioned immutable aggregate snapshot capped at **8 KiB and 2,000 tokens**; model output capped at **250 tokens and 1,000 UTF-8 characters** and schema-checked before rendering.

Proposed AI spend ceilings (not yet approved): **$0.05 maximum reserved cost per request, $0.25 per UTC day, and $5.00 total through Dec 15**. Before each call, compute a worst-case reservation from the selected model's current official input/output token rates and the token caps, then atomically reserve against daily and lifetime budgets. If the model/rate sheet is unknown, changed, or makes the maximum exceed the per-request ceiling, make no call. Commit the full reservation conservatively if the task times out or usage is unavailable; reconcile actual usage when available but never refund an ambiguous run into an available budget. Require separate owner approval of the model and dollar ceilings; otherwise Workflow remains disabled and the deterministic fallback is used. These proposed amounts are hard implementation limits, not a provider authorization.

At the current published Render `flex` maximum (1 CPU + 4 GB RAM, $0.40/hour) and a 60-second timeout, 50 full-duration runs would be approximately **$0.34 maximum compute**, plus task-state retention (inputs/outputs retained 30 days at $0.25/GB-month), service build/pipeline, egress and other account charges. This arithmetic is a planning bound under today's published rate, not an account quote or spend authorization. Recheck pricing and enforce an owner-approved total Render ceiling at provisioning time.
